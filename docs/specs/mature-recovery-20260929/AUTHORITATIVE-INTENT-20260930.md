# Authoritative product intent clarification — 2026-09-30

Authority: **USER INTENT — current explicit clarification in the active recovery session.** This supersedes narrower assistant interpretations in the recovery dossier. It does not by itself bless any particular current implementation.

## Melosviz

Melosviz is intended to be a **multi-scene visual generation and production system conditioned on an audio work**, not a single-scene generator.

Canonical outcome model:

> Given an audio file plus user/product configuration, programmable rules and other selected controls, generate a unique multi-scene visual work whose scene structure, timing and content align meaningfully with the audio.

Representative scale includes a roughly three-minute graphics-driven music video and the previously discussed festival/live context. The system must support compositions containing multiple scenes and potentially heterogeneous scene-generation/rendering techniques. Audio alignment may include beat/rhythm alignment and broader semantic/musical alignment; these are distinct signals and should not be collapsed into BPM-only synchronization.

Intended output/use projections include, at minimum:
- YouTube/music-video visualizations and other offline long-form output;
- short-form visual output;
- other long-form audiovisual work;
- real-time/live-audience situations where the mature architecture supports them.

The product is therefore not defined by one renderer or one scene type. Scene generation is a constituent capability inside a composition-level system.

## Consequences for mature-first recovery

1. **Multi-scene composition is normative product identity**, not merely an adversarial test case. Scene identity, ordering, transition/timeline semantics, cross-scene coherence and assembly are central obligations.
2. The current double-iteration, scene-type result collapse, inert selective-rerender selector and disconnected assembly are especially severe because they violate the product's core unit of work.
3. The mature ontology must include Composition/Project → audio/time/semantic analysis → scene plan/sequence → scene instances/revisions → heterogeneous generation/render execution → transitions/assembly → evidence/review/delivery/live projection.
4. A CVP may narrow scene count/renderers/output mode, but it must remain an encapsulated **multi-scene** product slice. A single-scene demo cannot stand in for the product spine.
5. Offline render/export and real-time/live are projections over shared audio/timeline/scene intent where feasible; architecture must explicitly model where their execution semantics diverge.
6. Existing April/hybrid/studio historical evidence should be reconciled against this current authority. This clarification is sufficient to stop treating multi-scene/hybrid-capable composition as merely unverified assistant inference.
7. SOTA/existence research should ask which existing systems can supply constituent analysis, timeline, DCC/render, generative and live primitives while preserving Melosviz's composition-level programming/control/evidence contract. It should not ask whether a generic single-scene generator obviates Melosviz.

Those remain research/design obligations.
